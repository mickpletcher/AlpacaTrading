# 007 Community and Accessibility Requirements

## Goal

Complete the repository's missing community standards and address concrete accessibility barriers in repository-owned documentation, the local journal, and generated reports.

## Requirements

1. Inspect GitHub's actual community profile and existing policies before choosing changes.
2. Supply a code of conduct, contribution guide, support guide, issue forms, and pull request template using the verified repository owner and reporting routes.
3. Preserve the MIT License, existing security invariants, private vulnerability reporting, protected-branch process, and trading component boundaries.
4. Keep a blank issue route available and make diagnoses, screenshots, and assistive-technology details optional for accessibility reports.
5. Define a truthful accessibility goal and known verification limits, not a blanket WCAG compliance promise.
6. Fix journal keyboard navigation, programmatic labels, readable contrast, focus, motion, dynamic feedback, and small-screen behavior.
7. Improve semantic structure and nonvisual alternatives in repository-generated HTML reports without changing calculations or trading logic.
8. Add repeatable regression coverage and record executed tests, failures, skips, and untested environments.
9. Use synthetic data only. Do not use credentials, contact brokerage accounts, or submit paper or live orders during validation.
10. Publish changes on a review branch and verify hosted checks. Verify GitHub community recognition only after an authorized merge to the default branch.

## Acceptance Boundary

A community checklist score does not certify accessibility or security. Complete assistive-technology testing, external host accessibility, and remediation of existing trading/security defects are outside this change. Disclose these limits in the accessibility statement and pull request.
